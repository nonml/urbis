# Q11.A — WebGPU Evaluation Spike (2026-06-25)

## Decision: GO (compute path only)

Primary render path stays **WebGL**. WebGPU compute shaders will be added as a progressive
enhancement for GPU-driven culling (Q11.B). The particle system requires no change — it
already achieves 50× count headroom via a WebGL2 closed-form vertex-shader approach (Q10.E).

**Interpretation:** Headless Chromium without a discrete GPU reports no WebGPU — this is
expected and matches CI. The probe is negative by environment, not by browser version.

**Browser reality (mid-2026):**
- Chrome 113 (May 2023) shipped WebGPU as stable. Chrome ~130+ as of mid-2026.
- Chromium/Edge market share: WebGPU available to ~88% of desktop web users.
- Three.js `WebGPURenderer` available since r153; actively maintained.
- WGSL spec: stable. Compute shaders: fully supported.

## Analysis

### GPU Particles (Q10.E)
Already handled. The renderer uses a closed-form vertex shader: each rain/snow drop is
animated by `uTime` with no per-frame CPU loop or buffer re-upload. This is functionally
equivalent to a GPU compute pass (no CPU ↔ GPU sync per frame). Adopting WebGPU compute
for particles would add complexity without a measurable win. **No action needed.**

### GPU Frustum Culling (Q11.B)
High-value target for WebGPU compute. Current CPU coarse cull + draw-all approach means
the GPU receives every mesh even when 60% is off-screen. A WebGPU indirect-draw pipeline
would:
1. Run a compute shader that writes a draw-indirect buffer (one entry per mesh).
2. Cull against camera frustum + Hi-Z pyramid entirely on GPU.
3. Issue a single `drawIndirect` call per material batch.

This is the core win WebGPU enables vs WebGL — WebGL cannot issue indirect draws from
compute results without round-tripping to CPU.

### Main Render Path
**Stay on WebGL.** Reasons:
- Safari (iOS/macOS) WebGPU support is partial as of 2026; mobile Safari has ~32% market share.
- Porting the 6900-line `renderer3d.js` to `WebGPURenderer` is a multi-quarter effort with
  high regression risk at this stage.
- WebGL2 is universally available and meets our visual quality bar (proven by Q9/Q10).

## Recommendation Summary

| Area | Decision | When |
|---|---|---|
| Particles | Stay on WebGL2 vertex shader | Already done |
| GPU frustum cull | GO — WebGPU compute + indirect draw | Q11.B |
| Hi-Z occlusion | GO — WebGPU compute | Q11.B |
| Main render path | WAIT — stay WebGL | Q13+ if at all |

## Easy Wins Added

`src/render/webgpu_support.js` — async `detectWebGPU()` utility that:
- Returns `{ available: bool, features: [], limits: {} }` in headed Chrome.
- Returns `{ available: false }` gracefully in headless/no-GPU contexts.
- Used by Q11.B culling implementation to decide between WebGPU and CPU cull fallback.
